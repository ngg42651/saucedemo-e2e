# SauceDemo E2E 자동화 — 설계 문서

작성일: 2026-08-23
상태: 승인됨 (구현 계획 작성 대기)

## 1. 목적

두 가지를 동시에 만족시킨다.

1. **취업 포트폴리오** — QA 자동화 채용 공고가 이름 그대로 요구하는 스킬(Playwright .NET, Page Object Model, xUnit, CI)을 실물로 증명한다. 이력서에 링크 하나로 제출 가능한 상태가 목표다.
2. **Claude 에이전트 팀 구조의 1~3단계 검증** — CLAUDE.md 축적, 리뷰 에이전트 분리, 계획/구현 분리가 실제로 작동하는지 확인한다.

두 목적이 충돌하면 포트폴리오를 우선한다. 팀 구조는 이 프로젝트가 끝난 뒤에도 다음 프로젝트에서 이어서 검증할 수 있지만, 포트폴리오는 이 저장소가 전부이기 때문이다.

## 2. 대상 선정 근거

### 왜 웹 자동화인가

이전에 진행하던 FlaScribe(데스크톱 UI 자동화, 2026-08-23 중단)는 데스크톱 축이고, 지원 후보 기업 다수는 `Playwright(.NET)` 또는 `Selenium C#`을 공고에 명시한다. 웹 자동화 포트폴리오는 FlaScribe로 대체되지 않는 별도 항목이다.

또한 팀 구조를 처음 도입하는 프로젝트는 기술적으로 지루해야 한다. 새 프로세스와 새 기술을 동시에 시험하면 실패했을 때 원인을 분리할 수 없다. 웹 자동화는 성공 판정이 `dotnet test`의 종료 코드로 자동화되므로, 에이전트가 진행 상황을 잘못 보고해도 즉시 드러난다.

### 왜 Playwright인가

Selenium 대비 자동 대기가 기본 내장이라 명시적 대기 코드가 줄고, 병렬 실행과 trace 기록을 별도 도구 없이 지원한다. 후보 기업 공고에서도 Playwright를 먼저 지목하는 경우가 많다.

### 왜 SauceDemo 단일인가

로그인 → 상품 목록 → 장바구니 → 체크아웃이 하나의 흐름으로 이어져 실제 서비스에 가깝다. 이 연속성이 있어야 "테스트 시나리오를 어떻게 설계했는가"라는 서사가 성립한다.

TheInternet(드래그, iframe, alert 등)은 기술 난이도가 높은 케이스 백화점이지만 케이스가 서로 무관해 Page Object 구조가 얕게 나온다. 두 사이트를 모두 다루면 범위가 두 배가 되어 목표 기간(2~3주)을 넘긴다.

## 3. 저장소 구조

```
/src
  Pages/          LoginPage, InventoryPage, CartPage, CheckoutPage
  Components/     HeaderMenu, CartBadge
  Support/        TestBase, Config, TestData
/tests
  LoginTests.cs  InventoryTests.cs  CartTests.cs  CheckoutTests.cs
.github/workflows/ci.yml
CLAUDE.md
README.md
```

### 설계 결정

**Pages와 Components를 분리한다.** 헤더 메뉴와 장바구니 배지는 모든 페이지에 나타난다. 이를 각 Page 클래스에 중복 정의하는 것이 Page Object Model을 처음 쓰는 사람이 가장 흔히 저지르는 실수다. 공유 요소를 별도 컴포넌트로 분리하면 중복이 사라지고, README에 설명할 설계 근거가 생긴다.

**Page 클래스는 검증하지 않는다.** Page는 조작(클릭, 입력)과 조회(텍스트 읽기)만 제공하고, assert는 테스트 파일에서만 수행한다. 이 경계가 무너지면 테스트가 무엇을 검증하는지 테스트 파일만 읽어서는 알 수 없게 된다.

**셀렉터는 Page 클래스 안에만 존재한다.** 테스트 파일에 CSS 선택자나 XPath 문자열이 등장하면 UI 변경 시 수정 지점이 흩어진다.

**타깃 프레임워크**: `net10.0`. 작업 머신에 설치된 SDK가 10.0.302 단일이므로 그에 맞춘다. CI도 동일 버전으로 고정한다.

**프레임워크**: xUnit + `Microsoft.Playwright.Xunit`. `PageTest` 기반 클래스가 테스트마다 새 `BrowserContext`를 주므로 장바구니 상태가 테스트 간에 새지 않는다. 별도 직렬화 없이 병렬 실행한다.

## 4. 테스트 케이스 (20개)

| 영역 | 케이스 | 개수 |
|---|---|---|
| 로그인 | `standard_user` 성공 / `locked_out_user` 차단 메시지 / 잘못된 비밀번호 / ID 빈칸 / 비밀번호 빈칸 / 미로그인 상태로 `/inventory.html` 직접 접근 차단 | 6 |
| 상품 목록 | 정렬 4종(이름 A→Z, 이름 Z→A, 가격 낮은순, 가격 높은순) / 상품 상세 진입 후 목록 복귀 / `problem_user` 이미지 깨짐 검출 | 6 |
| 장바구니 | 담기 시 배지 수 증가 / 빼기 시 감소 / 장바구니 페이지 품목이 담은 것과 일치 / Reset App State로 비워짐 | 4 |
| 체크아웃 | 정보 입력 빈칸 검증 / 총액 = 소계 + 세금 계산 검증 / 주문 완료 메시지 | 3 |
| 기타 | 로그아웃 후 세션 무효 확인 | 1 |

### 케이스 선정 원칙

**의도적 결함 계정을 활용한다.** SauceDemo는 `locked_out_user`(로그인 차단), `problem_user`(이미지 깨짐) 등 결함이 심어진 계정을 제공한다. 이를 검출하는 테스트는 "자동화가 실제로 무엇을 잡아내는가"를 보여주는 근거가 된다.

**`performance_glitch_user`는 제외한다.** 의도적으로 응답을 지연시키는 계정이라 flaky 테스트의 원인이 된다. 제외한 이유를 README에 기록한다. 케이스를 몇 개 만들었는가보다 무엇을 왜 포함하고 제외했는가가 테스트 설계 역량을 보여준다.

**총액 계산 검증이 목록에서 가장 중요하다.** UI 요소를 클릭하고 화면 문자열을 확인하는 데 그치는 자동화와, 비즈니스 규칙(소계 + 세금 = 합계)을 검증하는 자동화를 구분하는 지점이다. 주의할 함정은 화면에 표시된 총액을 그대로 읽어 자기 자신과 비교하는 것이다. 개별 상품 가격을 합산해 기대값을 독립적으로 계산한 뒤 표시된 총액과 비교해야 한다.

**`problem_user` 이미지 검증은 `src` 속성 비교로 한정한다.** 픽셀 단위 비교는 도입하지 않는다. 유지보수 비용 대비 얻는 것이 없다.

## 5. 불변 규칙

프로젝트 `CLAUDE.md`에 명시한다. 어기려면 이 설계 문서를 먼저 수정해야 한다.

1. `Thread.Sleep`을 쓰지 않는다. Playwright의 자동 대기와 `Expect()`만 사용한다.
2. Page 클래스는 assert하지 않는다. 조작과 조회만 담당한다.
3. 셀렉터는 Page 클래스 안에만 존재한다. 테스트 파일에 CSS·XPath 문자열을 두지 않는다.
4. 테스트를 통과시키기 위해 assert를 약화시키지 않는다. 통과하지 못하면 통과하지 못했다고 보고한다.

4번이 핵심이다. 에이전트에게 구현을 맡길 때 가장 흔한 실패 양식은 검증을 느슨하게 만들어 초록색을 만드는 것이다. 이 경우 테스트 스위트 전체가 무의미해지지만 겉으로는 정상으로 보인다.

## 6. 마일스톤과 팀 단계 매핑

포트폴리오 진행과 팀 구조 도입을 같은 축에 얹는다. 별도 일정으로 두면 한쪽이 밀린다.

| # | 산출물 | 팀 단계 | 이 구간의 학습 목표 |
|---|---|---|---|
| M0 | 솔루션 스캐폴드, Playwright 설치, 빈 테스트 1개 통과 | — | 자동 판정 기준 확보 |
| M1 | 로그인 6케이스 + `LoginPage` | 1단계: 혼자 작업하며 CLAUDE.md 축적 | 반복되는 지적이 무엇인지 파악 |
| M2 | 목록 6케이스 + `InventoryPage` + `HeaderMenu` | 2단계: 리뷰 에이전트 투입 | 컨텍스트 분리 리뷰의 효과 측정 |
| M3 | 장바구니 4케이스 + 체크아웃 3케이스 | 3단계: 계획/구현 분리 | 계획 게이트가 잡아내는 설계 오류 |
| M4 | CI + README 테스트 전략 + 실패 trace | — | 마무리 |

**M1을 1단계에 배치한 이유**: 로그인은 가장 단순한 영역이다. 여기서 실제로 무엇이 잘못 작성되는지 관찰해야 CLAUDE.md에 넣을 규칙이 나온다. 규칙을 미리 상상해서 작성하면 지켜지지 않는 규칙만 쌓인다.

**M3을 3단계에 배치한 이유**: 체크아웃 총액 검증은 소계, 세금, 합계의 계산 순서와 반올림 규칙이 얽힌다. 계획 없이 바로 구현하면 4장에서 언급한 "화면 값을 자기 자신과 비교하는" 무의미한 테스트가 나오기 쉽다. 계획 단계에서 이를 미리 잡아내는 것이 3단계의 효용을 확인하는 지점이다.

## 7. 리뷰 에이전트 (M2 시점 도입)

`.claude/agents/reviewer.md`에 정의한다. 체크 항목의 순서가 곧 우선순위다.

1. assert 약화 여부 — 이전 커밋 대비 검증이 느슨해졌는지
2. 불변 규칙 4개 위반 여부
3. Page와 테스트의 책임 경계 침범
4. 중복 — 동일한 셀렉터나 대기 로직이 두 곳 이상에 존재

리뷰는 지적만 한다. 칭찬하지 않고, 요청 범위 밖의 개선을 제안하지 않는다. 반복적으로 나오는 지적은 CLAUDE.md의 규칙으로 승격시켜 애초에 발생하지 않게 한다.

## 8. CI

GitHub Actions, `ubuntu-latest`, Chromium 단일.

- **트리거는 `push`와 `pull_request`만.** 스케줄 실행을 붙이지 않는다. SauceDemo는 외부 공용 데모 사이트라 통제할 수 없고, 사이트 장애로 인한 실패 알림이 쌓이면 CI 신호를 무시하게 된다.
- **브라우저 매트릭스를 만들지 않는다.** SauceDemo에서 브라우저별 동작 차이가 드러나지 않는데 CI 실행 시간만 3배가 된다.
- **실패 시 Playwright trace를 아티팩트로 업로드한다.** 이것이 있으면 README에 실패 분석 절차를 기술할 수 있다. 신입 지원자의 포트폴리오에서 흔치 않은 항목이다.
- **재시도 횟수는 0.** flaky를 재시도로 가리면 자동화가 존재하는 이유가 사라진다.

## 9. README에 포함할 것

README는 코드만큼 중요한 산출물이다. 채용 담당자가 코드를 열어보지 않고 README만 읽을 가능성이 높다.

- 테스트 전략: 케이스 선정 기준, 커버리지를 어떻게 판단했는가
- 제외한 케이스와 그 이유 (`performance_glitch_user` 등)
- Page Object Model 구조와 Components를 분리한 근거
- `problem_user`로 검출한 결함
- 실패 시 trace 확인 절차
- 외부 데모 사이트에 의존한다는 명시

## 11. 완료 기준

다음 두 조건을 모두 만족하면 완료로 판정하고 다음 프로젝트로 넘어간다.

- **포트폴리오**: 20개 케이스 통과, POM 구조 확립, GitHub Actions 통과 배지, README 테스트 전략 작성. 이력서에 링크를 제출할 수 있는 상태.
- **팀 구조**: CLAUDE.md가 관찰에 근거해 축적되었고, 리뷰 에이전트가 실제 문제를 최소 1건 잡았으며, 계획/구현 분리로 설계 오류를 최소 1건 사전에 방지했다.
